# Guideline 1.2 remediation — October 24, 2026

Apple reviewed version 1.41 (84), submission c0d7073d-b58b-4a2d-9473-ffad45744b86, on an iPad Air 11-inch (M3). Its message identifies objectification of real people and asks for a revised binary. It does not identify the exact remaining screen. Removing App Store screenshots alone cannot change the reviewed binary.

## Findings and changes in this patch

- Report generation previously created an externally readable share token automatically. Generation now returns no default share; the owner can request an export on demand.
- Public `/share/[token]` pages now return 404. A token alone no longer authorizes the report JSON or image endpoints. Export access checks the actual photo owner, including the original anonymous actor for anonymous reports. Private responses use `private, no-store`.
- The web report publication checkbox and public-link copy/share fallbacks were removed, including the creator mock-report checkbox. Image file exports remain available.
- Upload inputs always resolve to private. Publishing requests return 410. Migration `0060_private_reports_only` clears all existing public flags, retains report records, and enforces a database constraint against republishing. Applying it also empties report-based public leaderboards and public-profile report lists.
- Native image downloads now use the existing authenticated fetcher. The render/cache version changes so old labeled export images are not reused by the updated app.
- The native report had an `Estimated rank: Top X%` feature. It has been removed.
- Export graphics still used status labels including Gooner, Stacy and Chadlite, along with population comparisons. These labels and comparisons were removed from image designs and creator poster rendering. Their unused classification/distribution code was deleted.
- Generated TikTok captions no longer assign a status or challenge viewers to score higher. Private measurements and numerical scores remain.
- Settings → Support has an explicit “Report harmful content” mail action and displays the support address. It opens the user's mail app; it does not silently send a report or establish a response SLA.

## What the four safeguards mean

These are capabilities, not four Settings toggles. Apple explicitly includes AI-generated content within 1.2.

| Safeguard | Practical meaning |
| --- | --- |
| Filtering | Prevent objectionable content from being generated or posted. A Settings row is not a substitute. This patch does not add a new image/text moderation system. |
| Reporting and timely response | Users need an accessible report path and an operational process that actually handles reports. The new mail action provides a contact path; someone must monitor and act on it. |
| Blocking abusive users | If users can encounter other users' content or interact with them, blocking must actually stop that exposure/interaction. With public reports removed, do not add a fake block-users button to an app with no other users to select. Any remaining social/creator content needs its own review. |
| Published contact information | Provide a working address/support page. Settings already had contact links; the safety path now makes the address explicit. |

The separate Creator Content subsection concerns creator content presented inside the app. Having a creator marketing/affiliate portal does not by itself establish that the native app displays a creator-content community.

## Release sequence and verification

This is source work, not an App Store submission. The production database migration has not been applied and this patch has not been deployed or submitted.

1. Build and test a new native binary. Current source marketing version is 1.45, but app.json and the Xcode project still specify build 84. Choose a fresh build number before upload; do not confuse local source with the 1.41 (84) binary Apple reviewed.
2. Test on iPad and iPhone: report generation/restoration, owner image exports, Settings safety mail action, and missing public/rank controls.
3. Coordinate backend deployment and native rollout. Installed older clients download image exports without authentication; enforcing owner-only image rendering breaks that older export path until clients update. Do not claim old binaries already contain these native changes.
4. Deploy the backend patch and apply `bun run db:migrate --only 0060_private_reports_only` once, through the existing migration runner. Do not run all unrelated pending migrations.
5. Verify old public pages, old tokens, non-owner IDs and publication requests cannot reveal/publish reports; confirm existing owners can still open and export their reports. Check that former public leaderboards/profile report lists no longer expose reports after migration.
6. Review remaining private numerical appearance scoring, sample reports, onboarding, subscription screens and linked website content for language Apple could interpret as objectification. Privacy and moderation controls do not guarantee approval of the underlying feature.

Verification completed in development: compiled public report route returned HTTP 404; production web build passed; 359 native tests passed; TypeScript in web/native; native test suite; focused ownership/publication/export tests; real PNG rendering tests; local database migration against a temporary table confirmed two reports retained, zero public, and publishing rejected. No production report records were changed.

## Draft App Review response — use only after the revised binary and backend are ready

Hello App Review,

Thank you for clarifying the concern. We have revised the app to remove public report publishing and public report pages. Reports are accessible only to their owner, and exports are limited to images the owner explicitly chooses to save or share.

We also removed appearance rank/status labels, estimated population rankings and comparisons, and competitive share-caption language. Battle and Leaderboard are absent from the revised native navigation. Settings includes a clear safety reporting and contact path.

Please review the newly attached binary, rather than the previously reviewed 1.41 (84). If any remaining feature still raises an objectification concern, could you identify its screen and the steps to reach it so we can address it directly?

Thank you.
